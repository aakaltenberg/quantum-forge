## Задание 1. Исследование моделей и инфраструктуры

### 1. Сравнение LLM-моделей

**Критерии:** качество ответов, скорость, стоимость, удобство развёртывания, соответствие требованиям безопасности (данные не должны покидать контур компании без необходимости).

| Критерий | Локальные Hugging Face (Llama-3, Mistral, Qwen) | Облачные OpenAI (GPT-4o-mini, GPT-4o) / YandexGPT |
|----------|--------------------------------------------------|----------------------------------------------------|
| **Качество ответов** | Высокое у моделей 7B–13B при правильном промптинге; сопоставимо с GPT-3.5. Уступает GPT-4 в сложной логике и следовании инструкциям. | GPT-4o – золотой стандарт для RAG; отличная генерация, точность и структурированность. YandexGPT лучше работает с русскоязычным контентом, но уступает в многоязычности. |
| **Скорость** | Зависит от GPU. На A100 (40GB) генерация 20–40 токенов/с – приемлемо для внутреннего бота. Без GPU слишком медленно. | API-задержка 1–3 секунды на ответ, высокая пропускная способность. |
| **Стоимость владения** | Капитальные затраты на GPU-сервера (аренда от 150 руб/ч для A100). Эксплуатация ~ 100 000+ руб/мес при постоянной нагрузке. | Оплата по факту использования: GPT-4o-mini ~0.15$ (~13 руб)/1M токенов, GPT-4o ~2.5$ (~200 руб)/1M, YandexGPT Pro 5: 1200 руб/1М токенов.  Отсутствие CAPEX. |
| **Конфиденциальность** | Полный контроль – данные не покидают периметр. Критично для SOC 2 и закрытых политик. | Данные передаются третьей стороне. OpenAI и Yandex предлагают enterprise-соглашения, но для строгих требований SOC 2 нужен аудит провайдера и Data Processing Agreement. |
| **Развёртывание** | Требует MLOps-компетенций, настройки vLLM/TGI, мониторинга. | Простая интеграция через SDK, нет инфраструктурной обузы. |

**Вывод для QuantumForge:**  
С учётом SOC 2, конфиденциальных спецификаций и желания масштабировать решение на внешних клиентов, **рекомендуется гибридный подход**:  
- Для внутреннего контура (закрытые политики, код, чувствительные данные) использовать локальную модель Mistral-7B (или её русскоязычный аналог), дообученную/промпт-инженерно адаптированную, с развёртыванием на собственном GPU-узле.  
- Для менее критичных вопросов из общей документации, где допустимо облако, применять OpenAI GPT-4o-mini/YandexGPT Pro 5 как экономичный и высококачественный API с подписанным BAA (Business Associate Agreement).
Гибрид даёт баланс безопасности и стоимости.

### 2. Сравнение моделей эмбеддингов

**Задача:** преобразовать 21 250+ документов (и растущий объём) в векторное представление для поиска.

| Критерий | Локальные Sentence-Transformers (BGE-M3, E5-large-v2) | Облачные OpenAI Embeddings (text-embedding-3-large) |
|----------|--------------------------------------------------------|------------------------------------------------------|
| **Скорость индексации** | На GPU 100–200 док/с; полный цикл начальной индексации займёт ~2-3 минуты на A100. | Через API ~50 док/с; индексация займёт около 7–10 минут. |
| **Качество поиска** | BGE-M3 мультиязычный, хорошо работает с техническим английским и финским. MTEB-бенчмарки близки к OpenAI. | Отличное качество, особенно на смешанных языках. OpenAI регулярно обновляет модель. |
| **Стоимость** | Бесплатно, требуется только GPU-инфраструктура (учтена в LLM-сервере). | $0.13 за 1M токенов; индексация 20k документов ~ 10M токенов ≈ $1.3 однократно, ежемесячное пополнение ~400 стр. ≈ $0.03/мес. Достаточно дёшево. |
| **Конфиденциальность** | Данные не уходят наружу. | Эмбеддинги создаются на стороне провайдера. |

**Вывод:**  
Для QuantumForge критично сохранить конфиденциальность внутренних политик и кода. Предлагается использовать **локальный Sentence-Transformer BGE-M3** с HuggingFace. Он поддерживает мультиязычность (финский, шведский, русский), работает быстро на GPU и не нарушает периметр безопасности. При необходимости можно дополнительно использовать облачный API для публичных документов, но единый локальный подход упрощает архитектуру и аудит.

### 3. Сравнение векторных баз ChromaDB и FAISS

| Критерий | ChromaDB | FAISS (CPU) |
|----------|----------|-------------|
| **Скорость поиска** | Для <100k векторов задержка ~5–10ms, достаточно быстро. | Для 20k – <5ms, превосходно. |
| **Скорость индексации** | Средняя, использует HNSW, построение индекса ~30 сек на CPU. | Быстрая индексация на CPU, <10 сек. |
| **Сложность внедрения** | API как у облачного сервиса, удобно с LangChain, встроенная фильтрация по метаданным, персистентность «из коробки». | Требует ручного сохранения индекса, менее дружелюбен к метаданным, но прост в основе. |
| **Поддержка и экосистема** | Активно развивается, удобная работа с коллекциями, можно обновлять документы. | Зрелая библиотека Facebook, низкоуровневая, но гибкая. |
| **Стоимость владения** | Бесплатно (open-source), может работать на CPU. Нулевая инфраструктурная стоимость. | Бесплатно, работает на CPU, минимальный overhead. |
| **Удобство для разработки** | Идеально подходит для прототипирования и production, интеграция с LangChain встроена. | Больше ручного кода, но максимальная производительность. |

**Рекомендация:**  
Учитывая, что QuantumForge требуется быстрое прототипирование и последующее масштабирование, а также наличие метаданных (источник, версия, владелец) для выявления устаревших документов, выбираем **ChromaDB**. Она обеспечит персистентность, фильтрацию по метаданным (Confluence-пространство, дата актуализации) и легко встраивается в LangChain. FAISS можно использовать как опцию для высоконагруженного поиска позже, но на старте ChromaDB ускорит разработку.

### 4. Рекомендуемая конфигурация сервера

**Нагрузка:**  
- Индексация при старте и ежедневная инкрементальная.  
- Обслуживание ~50 одновременных пользователей, поиск по векторной базе.  
- Локальная LLM для гибридного RAG (7B-модель, квантованная).

**Минимальная production-конфигурация для локального контура (Kubernetes pod или выделенная ВМ):**
- **CPU:** 8 vCPU (x86)
- **RAM:** 32 GB
- **GPU:** 1x NVIDIA A10 (24 GB) или A100 (40 GB) для комфортной работы с LLM и эмбеддингами.
- **Диск:** 100 GB SSD под образы и индекс.

**Почему GPU обязателен:**  
Генерация ответов на CPU для 7B-модели неприемлема (>60 сек на ответ). GPU ускоряет и эмбеддинги, и LLM, обеспечивая время ответа в пределах 3–5 секунд. Для облачного OpenAI-крыла достаточно CPU-нода с 4 vCPU / 16 GB.

### 5. Итоговые рекомендации и выбор конфигурации

С учётом требований SOC 2, конфиденциальности и планов масштабирования предлагается три варианта, лучшим считается **Вариант 2 (гибридный)**.

#### Вариант 1: Полностью облачный
- LLM: OpenAI GPT-4o-mini
- Эмбеддинги: OpenAI text-embedding-3-large
- Векторная БД: ChromaDB (облачная serverless или self-hosted в AWS)
- Инфраструктура: только CPU-под
- **Плюсы:** Минимальная сложность, быстрый запуск, оплата по факту.
- **Минусы:** Все данные уходят вовне, сложно пройти SOC 2 без дорогостоящего enterprise-соглашения с OpenAI, риск утечки конфиденциальных спецификаций.

#### Вариант 2: Гибридный (рекомендованный)
- **Внутренний контур** (политики, код, закрытые регламенты):
  - LLM: Mistral-7B-Instruct (локально на GPU, HuggingFace TGI)
  - Эмбеддинги: BGE-M3 (локально)
  - Векторная БД: ChromaDB (persistent volume в EKS)
- **Внешний контур** (общая Confluence, онбординг, менее чувствительные документы):
  - LLM: OpenAI GPT-4o-mini через API
  - Эмбеддинги: те же локальные для единообразия
- **Инфраструктура:** Узел с GPU (A10) в EKS для внутреннего контура, отдельный CPU-сервис.
- **Оценка стоимости:** ~$700/мес за GPU-инстанс (reserved) + API OpenAI ~$100/мес.
- **Преимущества:** Конфиденциальные данные остаются в периметре, SOC 2 проходится легче, масштабируемость и возможность экспорта внешнего контура клиентам.

#### Вариант 3: Полностью локальный
- LLM: Mistral-7B / Llama-3
- Эмбеддинги: BGE-M3
- Векторная БД: ChromaDB или FAISS
- Инфраструктура: 2×GPU-сервер для отказоустойчивости
- **Плюсы:** Абсолютный контроль данных, нет зависимости от вендора.
- **Минусы:** Высокий порог входа, стоимость GPU 24/7 ($1500+/мес), необходимость MLOps-компетенций в команде.

#### Вариант 4: Serverless RAG от Yandex Cloud / AWS Bedrock
- Использование управляемых RAG-сервисов (YandexGPT + Yandex Search API или Bedrock Knowledge Bases).
- **Не рекомендуется** из-за юрисдикции данных (Финляндия/Эстония) и требований SOC 2, не все сервисы доступны в европейском регионе.

**Обоснование выбора Варианта 2:**
- Разделение чувствительных и публичных данных позволяет уже сегодня запустить бота для 80% запросов (онбординг, саппорт, общая документация) на быстром облачном стеке.
- Критичные для аудита документы обслуживаются локальной LLM с полным контролем.
- Архитектура естественным образом масштабируется: внешний контур можно оформить как продукт для клиентов (SaaS Digital Twin documentation assistant), а внутренний останется закрытым.
- Соответствие SOC 2 упрощается, так как аудиторы оценят разделение данных и шифрование.

**Заключение по Заданию 1:**  
Для реализации RAG-бота принято решение использовать **гибридную архитектуру** с локальными моделями для чувствительных документов и облачным OpenAI для некритичных, единой векторной базой ChromaDB и локальными эмбеддингами BGE-M3. Инфраструктура базируется на AWS EKS с GPU-нодой для on-premise LLM. Это оптимальный баланс безопасности, стоимости и гибкости.
